## 0. 摘要（先看这一段）

1. 现有 AI 是**"逐指令在线贪心 + 单步候选比较"**：先启发式打分，再对前 K 名做一次 `applyCommand` + `evaluate` 差分。没有回合级规划、没有对手建模、没有跨回合经济规划。
2. **不存在作弊读取**：游戏本身无战争迷雾（GDD 明文），UI 对每名玩家公开据点/单位/资金/得分与全部生产队列，AI 读的每个字段玩家都看得到。
3. 动作空间**完整**（与内核 `Command` 一一对应），但**质量差**：中盘实测 177 条候选里 155 条是"四处走"，攻击/占领常为 0 条 —— 战术必须靠多步组合表达。
4. 评估函数**把经济与扩张压到了噪声级**（村落收入权重 0.5、单座村落只值 150 分，而一次普通攻击就值 220 分），且完全没有威胁图、兵种克制、修理、比分意识。
5. **实测硬伤（切片 0 评估台，真实地图 60 局）**：`normal 100% 胜 easy`，但 **`hard` 只有 11.7% 胜 `normal`（95% CI 5.8%–22.2%）—— 难度阶梯在真实地图上倒挂**。原因就是第 4 条：hard 的 `cohesion`（抱团）主动惩罚分散占点，在 24×24、12 座村落的经济地图上等于自断经济。单测里"hard 8/8 胜 normal"是 fixtures 小地图上的假象（A/B 验证：把平局打破关掉仍是 18.8%，证明是既有问题，非本次改动引入）。

## 1. 当前 AI 的决策流程：它如何选择动作？

**调用链**

```
pveSession.stepAi()                      每 450ms 一次（DEFAULT_ACTION_DELAY_MS）
  └─ nextCommand(state, actor, difficulty, data, rng)   纯函数，返回"一条"指令
       ├─ 阶段分派：DEPLOY → pickDeploy() / PLAYING → pickPlay()
       └─ 结果交给 applyCommand() 执行 → emit() 刷新视图 → 若仍轮到 AI 则继续排程
  └─ 兜底：MAX_AI_STEPS = 40 条指令后强制 endTurn
```

**pickPlay（行动阶段）的六步**

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | `playCommandsFor(state, playerId)` | 枚举**全部**合法指令（实测中盘 177 条） |
| 2 | `scorePlay()` 逐条启发式打分 | 免克隆；按 `attack / move / capture / produce / wait` 分类打分 |
| 3 | 过滤 `endTurn`，取启发式最优 | 若最高分 ≤ 0 → 直接 `endTurn` |
| 4 | 按分数降序，取前 K 名 | K = `lookaheadK`：easy 0 / normal 5 / hard 12 |
| 5 | 对前 K 名逐个 `applyCommand`（**JSON 深克隆整个 state**）+ `evaluate` 差分 | 只有这 K 步是"精确"的 |
| 6 | 取 delta 最大者；分差 < ε=2 的并列候选用种子化 rng 任选 | 切片 0 新增，用于让种子有意义 |

**pickDeploy（部署阶段）**

- 按固定计划 `['sword','spear','sword']`（正好用满 3000 预算）选兵种；
- 落点 = "离敌方王城最近"（`24 - chebyshev`），hard 额外奖励"贴近已放置友军"；
- easy 则兵种与落点全随机。

**本质判定**：这是一条 **1 步前瞻的贪心策略**，每题只看"这一步之后"的静态分。`hard` 与 `normal` 的差别只是**候选宽度 5→12** 加两个风格权重（集火 0.15→0.6、抱团 0→3）。

## 2. 它能看到什么？有没有作弊读取？

**结论：没有作弊读取。** 三条证据：

| # | 证据 | 位置 |
|---|---|---|
| 1 | MVP **没有战争迷雾**（"视野"字段为将来预留、**不参与任何计算**） | `docs/gdd.md:146`、`:356` |
| 2 | 界面对**每一名玩家**显示：据点数量、单位数量、**资金**、得分 | `src/ui/GameScreen.tsx:430-442` |
| 3 | 界面的"生产队列"列出**所有玩家**的待出场订单（"我方" / 对方昵称） | `src/ui/GameScreen.tsx:550-569` |

AI 读取的字段（`GameState` 全量）：`units` / `buildings`（含占领进度）/ `funds`（含对手）/ `pending` / `deploy` / `turnSeq` / `round` / `phase` —— **每一项都在上述 UI 中可见或可直接推断**（单位位置与血量在棋盘上；据点归属与占领进度在棋盘上）。

**要注意的两点（不是当前问题，是未来约束）**

1. AI 用了 `state.funds[other]` 与 `state.round`（回合上限意识）——都在公开状态内且 UI 有展示，判定公平。
2. GDD 把"战争迷雾"列为首个后续版本（`:356`，需把"广播单一快照"改为"按玩家裁剪快照"）。**一旦加迷雾，AI 的信息裁剪必须与 UI 完全一致**（架构上要预留在同一处裁剪函数里），否则"公平 AI"这条硬约束会被破坏。

## 3. 动作空间有哪些？是否完整？

| 指令 | 生成来源 | 中盘实测条数 | 备注 |
|---|---|---|---|
| `deploy` | 6 兵种 × 部署区内可通行空格 | 部署期 ~数百 | 预算 3000、上限 4 个 |
| `deployDone` | 已放置 ≥1 个单位 | 1 | |
| `move` | 每未移动单位：Dijkstra 可达格（步 3 / 骑 6） | **155** | 数量主因 |
| `attack` | `attackableTargets`（射程内敌方单位） | **0**（该局面无接敌） | 间接单位移动后不可攻击 |
| `capture` | 脚下有非己方据点且兵种可占领 | **0** | 仅刀盾/长枪 |
| `produce` | 己方兵营 × 可负担兵种（每营每回合 ≤2 单、总量 ≤32） | **6** | |
| `wait` | 每个未行动单位各一条 | 15 | 防止回合卡住 |
| `endTurn` | 恒有 | 1 | |
| ~~`resign`~~ | **故意不生成** | — | AI 永不投降（设计意图） |

**完整性判定：完整。** `legalCommandsFor` 与内核 `commands.ts` 的校验一一对应，并由 `tests/unit/game/legalCommands.test.ts`（22 条）逐条断言"产出的每条指令都能被 `applyCommand` 接受"。

**但要正视两个结构性问题**

1. **一条指令 ≠ 一个战术**：本作没有"移动并攻击"的复合指令，所以"走位→集火"必须靠多步组合表达 —— 而当前只做单步前瞻，无法表达组合。
2. **`repair` 不在动作空间**：据点回血是 START 阶段自动的（`rules.repairPerTurn = 20`，`src/game/state.ts:125`），所以"撤退修理"只能是**站位目标**（把残血单位送到己方据点上），不是一条指令。评估函数与移动打分都要为它留项。

## 4. 评估函数考虑了什么、忽略了什么

**算了什么**（`src/ai/evaluate.ts`）

| 维度 | 现值 | 问题 |
|---|---|---|
| 材料 | `Σ cost × (hp/hpMax)`，己方正、敌方负 | 合理；但**不含 `pending`**（已付费未出场的单位 = 0 分 → "下单即亏分"的错误信号） |
| 据点 | `(hq 6 / barracks 3 / village 1.5) × 100 + income × 0.5` | 权重看似高（王城 600），但**收入项只有 0.5/点**：一座村落（收入 400）只值 200 分 |
| 占领进度 | 仅"**我方**正在占领" ×25/点 | **没有"敌方正在占领我据点"的负分** |
| 王城距离 | 我单位 `8 × (12 − d)` 加分；敌单位逼近我王城 `10 × (12 − d)` 扣分 | 只对王城敏感，其他据点无距离价值 |
| 地形 | `defense × 60` | 只算"站得高"，不算"暴露在多少火力下" |
| 资金 | `0.05` × (己方 − 各方) | 相抵后接近噪声 |
| 抱团 | `−cohesion × 距己方重心距离`（仅 hard） | **在扩张地图上是负收益**（见第 5 节第 1 条） |
| 终局 | 胜 `+1e6` / 淘汰 `−1e6` | 正确 |

**完全没算**（按缺失的杀伤力排序）

1. **威胁图**：哪些格子被敌方火力覆盖、覆盖多少伤害（防守与生存判断全靠 `scoreMove` 里"2 格内敌人数 × −25"这一条粗罚）。
2. **兵种克制**：`matchup.json` 的伤害表**从未被 AI 使用**（枪克骑 75、盾克步 80、骑克弓 75…全部浪费）。
3. **射程与站位关系**：投石车（2–3 格、不可反击）、弓兵（2 格）该保持的安全距离，AI 无概念 —— 反而会用它们去"拱王城"。
4. **修理与撤退价值**：站己方据点回 20 血（免费、不可关闭）这条免费资源完全没利用。
5. **比分与回合上限**：GDD 9.2 的兜底计分（据点分 5/3/1 + 兵力分 + 军费分）**已有现成实现 `scoreOf()`**，AI 却一次都没调用。
6. **生产的时间价值**：下单到出场延迟 1 个回合（下一 START），期间"已付费、未上场"。
7. **兵力上限 32**、**通行成本/机动性**（骑 6 格在 24×24 地图上的战略意义）、**桥头/关隘控制**（首发地图仅 3 座桥，是天然胜负手）、**多据点占领优先级**、**敌方集结预警**。

## 5. 五个主要弱点（按影响排序）

**① 经济与扩张被压到噪声级 —— 这是难度倒挂的直接原因**

- `income × 0.5` 使"每回合 +400 军费"的村落只值 200 分，而一次普通攻击（伤害 55）已值 220 分；`capture` 的固定分（40 + 进度 ×6）也远低于攻击收益。
- 24×24 地图有 **12 座中立村落**，全占满时收入从 1800 → 4200/回合（GDD 6.2），经济是胜负手。
- **hard 的 `cohesion = 3` 还主动惩罚"离开己方重心"** → 越是"困难"难度越不分散占点。
- 证据：`normal 100% 胜 easy`（easy 不占点→必输）说明占点=胜负手；同时 `hard` 仅 `11.7% 胜 normal`（60 局；关掉平局打破的 A/B 复测 18.8%，同向）。

**② 逐指令贪心、没有回合级与跨回合规划**

- 每步独立决定，无法执行"先走位、再集火"、"留一个单位守家、其余抢点"、"这回合先修血、下回合再推"。
- 更隐蔽的代价：**它无法评估"这步之后我还有 N 个单位没动"**，因此对"用掉唯一一次行动"的机会成本不敏感。

**③ 零对手建模（没有威胁图）**

- 走位只看"目的地 2 格内敌人数"，不看"我在这里会被打多少、会不会被反杀、会不会被投石车白嫖"。
- 历史上曾尝试"扣掉对手回手威胁"的手工惩罚项，实测把 hard 从全胜打到 50% —— **教训：对手建模要么用真搜索，要么用严格验证过的评估项，不能拍脑袋加减分**。

**④ 生产与兵种选择近似随机**

- `produce` 分 = `cost × 0.15`（+ 富余 25），并按 `unitList` 顺序取第一个买得起的 → 不做克制（对面爆轻骑不会出长枪）、不看兵营出战位是否被占（顺延白亏一回合）、不看兵力上限、不把闲置军费转成兵力（GDD 6.3 的"收入→产能"兑换完全没利用）。

**⑤ 占领博弈缺失**

- 不打断敌方占领（不知道"再拖一回合就丢据点"）；不为自己正在丢的据点回防；不知道"据点血量越高占领越快"（`+floor(HP/10)`），因此不会"先回血再占"。

*次级项*：回合上限 30 的比分意识缺失、`scoreOf()` 未使用、桥头/关隘与地图控制零概念、`pending` 未计入材料分。

## 6. 三种改进方案对比

**性能基座（本机实测）**：单节点 = `applyCommand` 0.047ms + `evaluate` 0.0094ms ≈ **0.056ms**；中盘分支因子 **177**；当前 hard 单步 p95 = 2.9ms（空载）/ 6.8ms（有负载）。

| | 启发式增强 | 极小极大 + α-β | MCTS |
|---|---|---|---|
| **做法** | 重写 `evaluate` + `scorePlay` + 生产/占领/威胁规则 | 候选按启发式排序 + beam + α-β 剪枝，2 层（我→敌）或 3 层 | UCB 树 + 随机 rollout 到回合结束 |
| **适用性** | ★★★★★ 所有难度都要它（它同时是搜索的排序与叶评估） | ★★★★☆ 适合"困难/专家"，行为可解释、可控 | ★★☆☆☆ 战斗完全确定（无命中率/暴击），采样优势被削弱 |
| **性能预算** | 几乎零增长（免克隆，仍是 10⁻²ms/候选） | 2 层 beam（24×16 ≈ 400 节点）≈ **22ms** ✅；全宽 2 层（177² ≈ 3.1 万节点）≈ **1.75s** ❌；3 层 beam（≈6100 节点）≈ **340ms**，只在 Worker 内可用 | 单次 rollout（到回合结束）= 几十~上百节点 ≈ 5–15ms；1000 campaigns ≈ **5–15s** ❌ 浏览器内不可行（除非限定局部战场 + 少量 campaign） |
| **开发成本** | 低（1 个切片，纯函数改造） | 中（1 个切片 + 时间盒/迭代加深 + 单测） | 高（随机 rollout 策略、UCB、时间管理、可复现的种子化采样） |
| **风险** | 低（可逐项开关、可回退） | 中（历史"过度保守"翻车先例；必须用评估台把关） | 高（成本高、结果难解释、性能不可控） |
| **本项目结论** | **做，作为基础层** | **做，作为 expert 档主线**（beamb + α-β + 时间盒） | **不做**；仅列长期可选（局部战术 MCTS 可用于验证，不作为交付） |

## 7. 建议的难度分级矩阵

四档同时定义"**玩家能感知的行为差异**"与"参数"（`▲` = 本档开启）：

| 参数 / 行为 | 简单 easy | 普通 normal | 困难 hard | 专家 expert |
|---|---|---|---|---|
| 候选集 | 随机取前 3 | 启发式 top 5 | 启发式 top 12 | top 16 + 敌方 top 8 |
| 评估器版本 | v1（现状） | v2 基础（含扩张/占点） | v2 完整（威胁图/克制/修理） | v2 完整 |
| 搜索 | 无（噪声贪心） | 1 步差分 | 1 步差分 | **2 层 beam 极小极大 + α-β** |
| 时间预算 | — | ≤10ms | ≤30ms | **≤150ms（Web Worker）** |
| 失误率 | 高（25% 直接过手、随机部署） | 少量（ε=2 平局打破） | 极少 | 几乎为零 |
| 扩张/占点 | ❌ 随机 | ▲ 会抢点 | ▲ 会抢点 + 优先级 | ▲ 会抢点 + 经济规划（军费→产能） |
| 集火残血 | ❌ | ▲ | ▲ | ▲（含"两回合能打死"预判） |
| 抱团协同 | ❌ | ❌ | ▲ | ▲（含"保护远程/投石车"） |
| 撤退修理 | ❌ | ❌ | ▲ | ▲ |
| 守家 / 打断占领 | ❌ | ❌ | ▲ | ▲ |
| 兵种克制出兵 | ❌ | ❌ | ▲ | ▲（含对手阵容反制） |
| 比分/回合上限意识 | ❌ | ❌ | ❌ | ▲ |
| 玩家感知 | "会漏操作，像新手" | "会打人、会抢点" | "会守家、会针对出兵" | "会预判、会协同、几乎不失误" |

**两条必须写进文档的说明**

1. **`hard` 的语义需要重定义**：现状 hard 在真实地图上弱于 normal（11.7%），重定义后 hard = "normal 的强化版（威胁图 + 守点 + 克制 + 撤退）"，符合玩家对"困难"的预期。值域不变（仍为 `'easy' | 'normal' | 'hard'`），`pveStore` 只校验值域 → **存档/联机兼容性不受影响**；唯一"破坏"是旧存档里选过 hard 的玩家会感觉 AI 变强了（这正是本次目标）。
2. **新增 `'expert'`** 需要同步：`Difficulty` 联合类型、`PROFILES`、`PveSetup.tsx` 的选项表、`pveStore.ts` 的 `DIFFICULTIES` 校验数组（否则新难度存档会被判非法而清档）、以及一个 E2E 断言。

## 8. 自动对战评估方案

**已交付（切片 0）**：`scripts/ai-bench.ts`（`npm run bench:ai`）+ `docs/ai-baseline.md`
- 30 种子 × 2 座位互换 = **60 局/对阵**，真实地图与真实数值；
- 每局独立 rng（`hashSeed(master, gameIndex)`），全参数可复现；
- Wilson 95% CI；镜像局先手平衡；单步决策耗时 p50/p95。

**三类基准对手（必须有，否则"变强"无法证明）**

| 基准 | 实现方式 | 用途 |
|---|---|---|
| **旧 AI（版本快照）** | 把 v1.2.0 的 `src/ai/index.ts` 冻结为 `src/ai/legacy/v1.ts`（`legacyNormal` / `legacyHard`） | 回归对照："新 hard vs 旧 hard"，证明改动真的变强而不是换了个风格 |
| **随机 AI** | `uniform`：在 `legalCommandsFor` 上均匀随机（不学不动、不用评价） | 底线门槛：任何档位必须 ≥95% 胜它（防"评估函数改坏了也自我感觉良好"） |
| **脚本 AI（可解释）** | ① `turtle`：守王城与己方据点，不主动出击；② `rusher`：直线冲敌王城；③ `greedy-capture`：只抢村落、见敌就退 | 能力边界诊断：会不会被龟缩拖到计分输、能不能守住斩首、抢点速度够不够。这些不能用胜率一句话概括 |

**指标（胜率之外必须有行为指标 —— 这是"难度可感知"的量化证据）**

- 结果：胜率 + CI、平均大回合数、平均指令数、平局率、未终局率；
- 行为：每回合占领事件数、平均单位数、平均收入、与敌王城平均距离、集火成功率、撤退（回据点修理）次数、期末闲置军费；
- 性能：决策耗时 p50/p95/max（分难度、4 人局单独跑一遍）。

**统计纪律**：60 局 → CI 约 ±10pp；要判定"提升 5%"需 ~400 局（一次约 15 分钟）→ 采用**门槛式验收**（如 ≥65% / ≥70%）+ **换主种子复跑一次**确认非偶然，避免为 5% 反复跑大样本。

## 9. 性能预算（浏览器）

**实测**：单节点 0.056ms；hard 单步 p50 1.1–2.3ms / p95 2.9–6.8ms；一局（~1500 条指令）在 Node 里约 1.2–2.5s。

**约束**：60fps 帧预算 16.7ms；AI 步与步之间有 450ms 间隔（`DEFAULT_ACTION_DELAY_MS`），可用于吸收"思考"。

| 档位 | 单次决策预算 | 位置 | 依据 |
|---|---|---|---|
| easy / normal | ≤10ms | 主线程可接受 | 一次 10ms 长任务 ≈ 掉 1 帧，且发生在 AI 回合（玩家无操作） |
| hard | ≤30ms | 主线程可接受（**上限**） | 30ms ≈ 掉 2 帧；超过就应移出主线程 |
| **expert** | **≤150ms** | **必须 Web Worker** | 2 层 beam ≈ 22ms，3 层 beam ≈ 340ms → 用时间盒迭代加深封顶 150ms；450ms 间隔足以吸收，UI 显示"思考中" |
| 4 人局 | 单回合 3 个 AI 连续行动 | — | 最坏 ≈ 3 × (450ms + 计算)；需在 `ancient_04` 上单独跑 bench 验证 |

**Worker 化成本（切片 4 要实测的两件事）**

1. 每次决策 `postMessage` 序列化 `GameState` 的量级与耗时（24×24、≤32 单位，预估 10–50KB，结构化克隆应在 1ms 内，但必须实测）；
2. 备选方案**协作式分片**：主线程内把搜索切成 <8ms 的片段、用已注入的 `schedule` 让出（改动最小、永不掉帧），代价是"计算仍在主线程"（不满足 §5 的字面要求，需你确认取舍）。

**风险登记（每条都有应对）**

1. 历史"扣对手回手威胁"把胜率打到 50% → **对手建模只走"真搜索"或"评估台验证过的评估项"**，不接受拍脑袋惩罚项。
2. hard 语义重定义会让旧存档的体验变化 → 值域不变、兼容性安全；CHANGELOG 里明写。
3. 4 人局（3 个 AI）与大地图未验证 → AI-4 之后补跑 `ancient_04` bench。
4. 本机 E2E 套件极慢（本次两次尝试 10/17 分钟无输出后中止）→ AI-5 起用 `--reporter=line` 按文件分批跑，发版前完整跑一遍。
5. `tsconfig` / bench 工具链：`bench:ai` 依赖本机 `rolldown`（Vite 8 依赖自带，零新增依赖）；若换机器需确认 `node_modules/.bin/rolldown` 存在。
