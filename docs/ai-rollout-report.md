# 切片 4 · 回合级 rollout（AI-4c）—— 设计 + 交付报告

> 阶段：切片 4 · 日期：2026-10-03 · 基线：`2df9825`
> 上游结论：切片 1 静态威胁项 0/16、切片 2 浅层搜索 51.7%、切片 3 评估器 v3 53.3%
> —— 三次都指向同一件事：**一个 ply = 一条指令**的框架下，"多搜一层"只是多算一个单位的动作，
> 看不到对手**整回合**能组织出的攻势。本切片换机制。

---

## 1. 机制：`value(我的一条指令) = evaluate(我走完这回合 → 对手走完这回合)`

```
对每个根候选指令 c（按启发式排序，取前 beamWidth 条）：
  1. apply(c)                          // 我的第一步
  2. 我按启发式贪心把这一回合走完        // rolloutMySteps 步（0 = 跳过）
  3. 补一个 endTurn（把手交出去）
  4. 对手用【与 hard 相同的 1 步前瞻】走完**整个回合**   // rolloutFoeSteps 步 ← 本机制的核心
  5. value(c) = evaluate(结果局面, 我)
取 value 最大的 c（ε 内并列用种子化 rng 任选）
```

**为什么第 4 步要用 1 步前瞻而不是纯贪心**：贪心比 `hard` 弱得多，用它推演对手会**低估威胁**，
AI 反而变得过于自信。实测也正是如此 —— 贪心版 12 局是 58.3%，换成 1 步前瞻后 20 局是 60.0%。

**为什么是确定性 rollout 而不是 MCTS**：本作战斗完全确定（无命中率/暴击），随机采样的优势被削弱；
更重要的是项目硬约束要求"刷新后 AI 逐帧可复现"，确定性贪心/前瞻 rollout 天然满足。

**成本控制**：开销大头同样是候选枚举（`playCommandsFor` 的 Dijkstra，约 1–3ms/次），
因此用 `rolloutBudget`（枚举次数上限）封顶 —— 预算耗尽时保留**已算完的候选**选优（各候选独立评估，
不需要像迭代加深那样丢弃整层）。

## 2. 新增参数（`AiProfile`，默认 0 = 不启用）

| 参数 | oracle 取值 | 含义 |
| --- | ---: | --- |
| `rolloutMySteps` | 6 | 我这一回合最多再走几步 |
| `rolloutFoeSteps` | 8 | 对手这一回合最多走几步 |
| `rolloutFoeLookahead` | 8 | 对手每步的挑棋宽度（0 = 纯贪心） |
| `rolloutBudget` | 140 | 单条指令的枚举次数上限（确定性） |
| `beamWidth` | 6 | 根候选条数 |

**评估沿用 `hard` 那一套（v3 四个开关全关）** —— 隔离变量：本切片只改机制，不动评估。

有单测断言两者决策完全一致）。`oracle` **不接入 UI**（设置页仍只有 easy/normal/hard）。

## 4. 验收结果：⚠️ 有效，但差一点到门槛

| 项 | 门槛 | 实测（60 局，真实地图） | 判定 |
| --- | --- | --- | --- |
| 强度 | `oracle` ≥65% 胜 `hard` | **63.3%（50.7%–74.4%）** | ⚠️ 差一点（但 CI 下界 >50%） |
| 延迟 | 整回合 ≤30s | 单步最坏 576.82ms ⇒ 最坏回合 ≈23s | ✅ |
| 合法性 | 非法指令 0 | 评估台内建断言无触发 | ✅ |
| 回归 | 既有单测不回退、前三档行为不变 | ✅（90 条 AI 单测全绿） | ✅ |

**这是四次尝试里唯一真正压过 `hard` 的机制**（+13pp 相对五五开）：

| 尝试 | 机制 | 胜率 |
| --- | --- | --- |
| 切片 1 | 静态威胁项 | 0/16（剧毒） |
| 切片 2 | 3 层 beam 搜索 | 51.7% |
| 切片 3 | 评估器 v3（四个手工项） | 53.3% |
| **切片 4** | **回合级 rollout** | **63.3%** ✅ |

**设计上被验证有效的一点**：把对手的推演从"纯启发式贪心"换成**与 `hard` 相同的 1 步前瞻**后，
胜率从 58.3%（12 局）升到 60.0%（20 局）→ 63.3%（60 局）。
**低估对手会让 AI 过于自信** —— 这个结论与切片 1"手工威胁项过度悲观反而翻车"正好互为镜像。

**仍不启用**：`oracle` 与 `master` / `expert` 一样**不接入 UI**（`PveSetup` / `pveStore` 仍只有三档）。
理由：63.3% 未达 65% 门槛；且它的单步耗时是 `hard` 的约 95 倍，按项目硬规则**必须先搬进 Web Worker**
（AI-6）才能上线。

**冲过门槛的下一步**（可选项）：加大 `rolloutFoeSteps`（8 → 12）与 `beamWidth`（6 → 8），
让对手模型更完整；代价是单步耗时约翻倍、最坏回合会顶到 30s 上限附近，需重新测 p95。
